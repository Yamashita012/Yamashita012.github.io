Before you can break Kerberos, you have to understand how it actually works. This is the foundational transmission: how Windows proves who you are.

Introduction

Every offensive Active Directory technique you will ever learn — Kerberoasting, Pass-the-Hash, Golden Tickets, ASREPRoasting, NTLM relay — is a deviation from normal authentication behavior. You cannot understand the deviation until you understand the baseline.

This article is that baseline. It walks through exactly what happens between the moment a user presses ENTER on the Windows logon screen and the moment they're sitting on their desktop with a mapped drive and an Outlook inbox open. No shortcuts, no hand-waving — packet by packet, message by message.

By the end, you'll understand:

  • How Windows turns a typed password into cryptographic material
  • Why NTLM still exists, and exactly how it works
  • Every message in the Kerberos exchange (AS-REQ → AS-REP → TGS-REQ → TGS-REP → AP-REQ → AP-REP)
  • How LDAP, certificate-based authentication, and Integrated Windows Authentication fit into the picture
  • Where common attack techniques intersect with the authentication flow — without turning this into an exploitation guide
// Note

This is a pre-requisite article for learning Kerberos attacks, not an attack tutorial itself. Exploitation techniques are mentioned only to show where they occur in the authentication process.

Why Authentication Matters

Active Directory is the identity backbone of most enterprise networks. Every file share, every SQL Server, every internal web app, every RDP session ultimately trusts a decision made by the authentication layer: "is this really who they claim to be?"

If authentication is compromised, everything downstream is compromised too — because Windows authorization decisions (ACLs, group membership, delegation rights) are only as trustworthy as the identity they're built on. This is why domain compromise chains almost always start by attacking authentication itself, not authorization.

// Warning

A huge percentage of real-world AD compromises trace back to authentication weaknesses — weak NTLM fallback, unconstrained delegation, or crackable Kerberos tickets — rather than a software exploit. Authentication is the attack surface, not just a gatekeeper in front of it.

Authentication vs Authorization

These two terms get conflated constantly, and the distinction matters for understanding the rest of this article.

ConceptQuestion It AnswersAD Mechanism
AuthenticationWho are you?NTLM, Kerberos, LDAP bind, certificates
AuthorizationWhat are you allowed to do?Access Control Lists (ACLs), group membership, the PAC

A Kerberos ticket proves identity. What that identity is allowed to touch is a completely separate decision made by the resource (a file server, SQL Server, etc.) using the Privilege Attribute Certificate (PAC) embedded in the ticket, cross-referenced against the resource's ACL.

concept
Authentication  →  "This is CONTOSO\jsmith, and I can prove it cryptographically."
Authorization   →  "CONTOSO\jsmith is a member of Finance-ReadOnly. Grant read access."

Section 1 — How Windows Authentication Works

This section covers the full journey from keystroke to Domain Controller contact — before we even get into NTLM or Kerberos specifics.

1.1 The User Enters a Username and Password

When a user types their credentials into the Windows logon screen (winlogon.exe → LogonUI.exe) and presses Enter, the plaintext password briefly exists in memory but is never sent across the network in plaintext, and Windows does not store it in plaintext on disk.

1.2 Password Hashing

NT Hash

Windows stores (and primarily uses) the NT Hash, which is simply the MD4 hash of the UTF-16LE encoded password.

formula
NT Hash = MD4( UTF16-LE( password ) )
// Note

Despite the name, this has nothing to do with "NTLM" as a protocol version — the NT Hash is the credential material; NTLM is the authentication protocol that uses it.

Why Windows Doesn't Store Plaintext Passwords

Storing plaintext passwords would mean a single database compromise (ntds.dit on a DC, or the SAM database on a local machine) instantly exposes every credential. Hashing is a one-way transformation — you can verify a password without ever needing to store it.

// Warning

The NT Hash is not salted and uses MD4, a cryptographically broken algorithm. This is precisely why NT Hashes can be used directly for Pass-the-Hash attacks — the hash itself is valid credential material, not just a "proof" of the password.

Where Hashes Are Stored

LocationScopeFile
SAM databaseLocal accountsC:\Windows\System32\config\SAM
NTDS.ditDomain accounts%SystemRoot%\NTDS\ntds.dit on each DC
LSASS memoryCurrently logged-on sessions (cached)In-memory only, volatile

1.3 Client Contacts the Domain Controller

Before any authentication protocol can run, the client has to answer a basic question: which server is my Domain Controller?

DNS Lookup and SRV Records

Windows doesn't hardcode a DC's IP address. Instead, it queries DNS for SRV (service) records that advertise which hosts provide the _kerberos, _ldap, and _kpasswd services for the domain.

dns srv records
_ldap._tcp.dc._msdcs.contoso.local
_kerberos._tcp.dc._msdcs.contoso.local
_kerberos._udp.contoso.local
_gc._tcp.contoso.local

This process is called DC Locator (DsGetDcName) and is handled by the Netlogon service on the client.

sequenceDiagram participant Client participant DNS participant DC as Domain Controller Client->>DNS: SRV query: _ldap._tcp.dc._msdcs.contoso.local DNS-->>Client: dc01.contoso.local (priority, weight, port) Client->>DNS: A record query: dc01.contoso.local DNS-->>Client: 10.0.0.10 Client->>DC: LDAP ping (CLDAP) to verify DC is alive DC-->>Client: NetLogon response (domain info) Client->>DC: Begin authentication (Kerberos/NTLM)
Fig. 2 — DC Locator process before authentication begins

Demonstrating DC Discovery

bash — nslookup

// Tip

If DC discovery fails, nothing downstream works — no Kerberos, no LDAP, no Group Policy. When troubleshooting a "can't log on" issue, always verify DNS and DC Locator first (see Section 9).

Once the client has located a DC, it proceeds to authenticate using either NTLM or Kerberos — which one depends on the context, and that's exactly what the next two sections cover.

Section 2 — NTLM Authentication

2.1 History

NTLM (NT LAN Manager) is Microsoft's legacy challenge-response authentication protocol, originally built to replace the even weaker LM (LAN Manager) protocol from the OS/2 era. Kerberos became the default for domain authentication starting with Windows 2000, but NTLM never fully disappeared.

2.2 When NTLM Is Still Used

ScenarioWhy NTLM Instead of Kerberos
Authenticating to an IP address instead of a hostnameKerberos requires an SPN tied to a name, not an IP
Workgroup (non-domain) authenticationNo KDC available
Legacy applications hardcoded to NTLMApplication-level limitation
Cross-forest scenarios without proper trust/SPN setupSPN resolution failure
Kerberos failure (clock skew, missing SPN, etc.)Windows silently falls back to NTLM
// Warning

This automatic fallback behavior is a major attack surface. An attacker who can force a Kerberos failure (or who targets a protocol that never supported Kerberos, like older SMB clients) can coerce a system into using the weaker NTLM protocol.

2.3 NTLMv1 vs NTLMv2

FeatureNTLMv1NTLMv2
Challenge size8 bytes8 bytes (client also sends its own)
HashingDES-based, weakerHMAC-MD5, stronger
Vulnerable to rainbow tablesYes (especially with LM)Much more resistant
Timestamp includedNoYes (replay protection)
Default in modern WindowsDisabled by policyEnabled

2.4 Challenge-Response: The Core Concept

NTLM never sends a password — or even a hash — directly over the wire. Instead, it proves knowledge of the hash through a challenge-response mechanism.

sequenceDiagram participant Client participant Server participant DC as Domain Controller (Netlogon) Client->>Server: NEGOTIATE_MESSAGE Server-->>Client: CHALLENGE_MESSAGE (8-byte server nonce) Client->>Server: AUTHENTICATE_MESSAGE (response = HMAC(NT Hash, challenge)) Server->>DC: Forward challenge + response via Netlogon (pass-through auth) DC-->>Server: Validated / Denied Server-->>Client: Access Granted / Denied
Fig. 3 — NTLM challenge-response flow

2.5 The Three NTLM Messages Explained

NEGOTIATE_MESSAGE

Sent by the client to initiate NTLM authentication. It advertises which NTLM capabilities the client supports (session security, signing, 128-bit encryption, Unicode support, etc.) via a set of negotiate flags.

ntlmssp_negotiate
NTLMSSP_NEGOTIATE
  Signature: NTLMSSP\0
  MessageType: 0x00000001
  NegotiateFlags: NTLMSSP_NEGOTIATE_UNICODE | NTLMSSP_NEGOTIATE_NTLM | ...

CHALLENGE_MESSAGE

Sent by the server (or resource) in response. It contains an 8-byte random nonce (the "server challenge") that the client must incorporate into its response — this is what prevents simple replay of a captured response.

ntlmssp_challenge
NTLMSSP_CHALLENGE
  Signature: NTLMSSP\0
  MessageType: 0x00000002
  ServerChallenge: 0x0123456789ABCDEF
  TargetInfo: (domain name, computer name, DNS info)

AUTHENTICATE_MESSAGE

The client computes a response using its NT Hash and the server's challenge, then sends this response — never the hash itself, never the password.

ntlmssp_authenticate
NTLMSSP_AUTHENTICATE
  Signature: NTLMSSP\0
  MessageType: 0x00000003
  LmChallengeResponse: ...
  NtChallengeResponse: HMAC-MD5(NTHash, ServerChallenge + ClientChallenge + ...)
  Domain / User / Workstation
// Note

Why doesn't the password cross the network? Because the server never needs the password itself — only proof that the client possesses the correct NT Hash. The server (or the DC, via Netlogon pass-through authentication) independently computes the expected response using its own copy of the NT Hash and compares it.

2.6 Demonstrating NTLM

Capturing the exchange in Wireshark: filter for the NTLMSSP messages inside SMB2 or HTTP traffic:

wireshark filter
ntlmssp

You'll see three frames corresponding to NEGOTIATE_MESSAGE, CHALLENGE_MESSAGE, and AUTHENTICATE_MESSAGE — typically nested inside SMB2 Session Setup requests/responses.

Checking NTLM usage on Windows:

# Enable NTLM auditing to see where it's still used in your environment

2.7 NTLM Vulnerabilities (Where They Fit In)

AttackWhat It Targets
Pass-the-HashUses a stolen NT Hash directly in the AUTHENTICATE_MESSAGE computation — no need to know or crack the plaintext password
NTLM RelayAn attacker relays a captured NEGOTIATE/AUTHENTICATE exchange to a different server before it expires, authenticating as the victim elsewhere
NTLM DowngradeForcing a client to use NTLMv1 or LM instead of NTLMv2, making offline cracking dramatically easier
Missing SMB SigningWithout signing, relayed NTLM traffic can be tampered with or replayed against SMB targets
// Mitigation

Disable NTLMv1, enforce SMB/LDAP signing, restrict NTLM via Group Policy (Network security: Restrict NTLM), and prefer Kerberos wherever possible. Enable Extended Protection for Authentication (EPA) on services that support it.

Section 3 — Kerberos Authentication

Kerberos is the default, preferred authentication protocol in Active Directory. It's also the protocol behind the majority of modern AD attack techniques, which is why understanding it thoroughly is non-negotiable for anyone working in this space.

3.1 History

Kerberos originated at MIT in the 1980s as part of Project Athena. Microsoft adopted a modified version (RFC 4120-compliant, with a proprietary extension called the PAC) as the default authentication protocol starting with Windows 2000.

3.2 Advantages Over NTLM

AdvantageExplanation
Mutual authenticationBoth the client and the server prove their identity — NTLM only proves the client's
No pass-through auth neededThe DC isn't contacted for every single resource access — tickets are reusable within their lifetime
Stronger cryptographyUses AES (in modern Windows) instead of MD4/DES-derived hashing
Delegation supportServices can act on a user's behalf against other services (when configured)
Ticket-based, not challenge-basedReduces the number of round trips per resource access
// Note

Microsoft prefers Kerberos because it dramatically reduces load on Domain Controllers (no pass-through validation per connection) while offering stronger cryptographic guarantees and mutual authentication that NTLM structurally cannot provide.

3.3 Core Kerberos Components

ComponentDescription
Client (Principal)The user or service requesting authentication
KDCRuns on every DC; combines the AS and TGS roles
AS (Authentication Service)Issues the initial Ticket Granting Ticket (TGT)
TGS (Ticket Granting Service)Issues service tickets based on a valid TGT
SPNUniquely identifies a service instance tied to an account, e.g., MSSQLSvc/sql01.contoso.local:1433
TicketEncrypted data structure proving identity, encrypted with the target's key
PACMicrosoft's extension embedding group membership/authorization data inside the ticket
Session KeySymmetric key shared between client and service for the duration of a ticket's use

AS-REP: TGT| Client Client -->|3. TGS-REQ: TGT + SPN| TGS TGS -->|4. TGS-REP: Service Ticket| Client Client -->|5. AP-REQ: Service Ticket| Service["Target Service"] Service -->|6. 3.4 The Full Kerberos Flow, Step by Step

Step 1 — AS-REQ (Authentication Service Request)

The client sends a request to the AS for a Ticket Granting Ticket (TGT). Modern Kerberos requires pre-authentication: the client encrypts a timestamp with a key derived from the user's password (AES key, derived via the NT Hash in legacy mode) and includes it in the request.

krb_as_req
KRB_AS_REQ
  cname: jsmith
  realm: CONTOSO.LOCAL
  sname: krbtgt/CONTOSO.LOCAL
  PA-ENC-TIMESTAMP: Encrypted(timestamp, key=derived from password)
// Note

Pre-authentication exists specifically to prevent an attacker from requesting a TGT for any username without knowing that user's key — this is what makes AS-REP Roasting possible only against accounts that have pre-authentication disabled.

sequenceDiagram participant Client participant AS as Authentication Service (KDC) Client->>AS: AS-REQ (username, encrypted timestamp) AS->>AS: Decrypt timestamp using stored user key AS-->>Client: AS-REP (TGT encrypted with krbtgt key, session key encrypted with user key)
Fig. 5 — AS-REQ / AS-REP exchange

Step 2 — AS-REP (Authentication Service Response)

If pre-authentication succeeds, the KDC returns a TGT encrypted with the krbtgt account's secret key (unreadable by the client), and a session key encrypted with the user's own key.

krb_as_rep
KRB_AS_REP
  cname: jsmith
  ticket (TGT): Encrypted(session_key, client_name, PAC, validity) [encrypted with krbtgt hash]
  enc-part: Encrypted(session_key, ...) [encrypted with user's key]
// Warning

Because the TGT is encrypted with the krbtgt account's key — never the requesting user's key — the client cannot read or forge its contents. This is exactly why the krbtgt account's hash is the single most sensitive credential in the domain (compromising it enables Golden Ticket forgery).

Step 3 — TGS-REQ (Ticket Granting Service Request)

When the client wants to access a specific resource (e.g., a file server), it presents its TGT to the TGS along with the SPN of the target service.

krb_tgs_req
KRB_TGS_REQ
  ticket: (the TGT from AS-REP)
  authenticator: Encrypted(client timestamp, session_key)
  sname: cifs/fileserver01.contoso.local
sequenceDiagram participant Client participant TGS as Ticket Granting Service (KDC) Client->>TGS: TGS-REQ (TGT + authenticator + target SPN) TGS->>TGS: Decrypt TGT with krbtgt key, validate PAC & authenticator TGS-->>Client: TGS-REP (Service Ticket encrypted with target service's key)
Fig. 6 — TGS-REQ / TGS-REP exchange

Step 4 — TGS-REP (Ticket Granting Service Response)

The TGS validates the TGT and authenticator, then issues a service ticket encrypted with the target service's own secret key (derived from that service account's password), plus a fresh session key.

krb_tgs_rep
KRB_TGS_REP
  ticket: Encrypted(session_key2, client_name, PAC) [encrypted with target service's key]
  enc-part: Encrypted(session_key2) [encrypted with previous session_key]
// Note

This is a critical detail: the service ticket is encrypted with the target service account's password-derived key — not the krbtgt key. This is exactly what Kerberoasting and Silver Ticket attacks target.

Step 5 — AP-REQ (Application Request)

The client presents the service ticket directly to the target service (no DC round-trip needed).

krb_ap_req
KRB_AP_REQ
  ticket: (the service ticket from TGS-REP)
  authenticator: Encrypted(client timestamp, session_key2)

The service decrypts the ticket using its own key, extracts the PAC, and validates the authenticator's timestamp to prevent replay.

Step 6 — AP-REP (Application Response) — Mutual Authentication

If mutual authentication is requested, the service proves its own identity back to the client by encrypting the client's timestamp with the shared session key.

krb_ap_rep
KRB_AP_REP
  enc-part: Encrypted(client timestamp) [encrypted with session_key2]
sequenceDiagram participant Client participant Service as Target Service Client->>Service: AP-REQ (Service Ticket + Authenticator) Service->>Service: Decrypt ticket with own key, extract PAC, validate authenticator Service-->>Client: AP-REP (mutual authentication, optional) Note over Client,Service: Session established — resource access begins
Fig. 7 — AP-REQ / AP-REP exchange

3.6 Ticket Lifetime and Renewal

SettingDefault Value (Domain Policy)
Maximum TGT lifetime10 hours
Maximum TGT renewal7 days
Maximum service ticket lifetime10 hours
Clock skew tolerance5 minutes

Tickets don't need to be re-requested from scratch — Kerberos supports renewal, where a still-valid (but expiring) TGT can be exchanged for a fresh one without re-entering credentials, up to the maximum renewal window.

3.7 Delegation

Delegation allows a service to act as the user against a second, downstream service — necessary for scenarios like a web server that needs to query a SQL Server on the user's behalf.

graph LR User -->|1. Authenticates| WebServer["Web Server"] WebServer -->|2. Acts as User| SQLServer["SQL Server"]
Fig. 8 — Basic delegation concept
Delegation TypeHow It WorksRisk Level
Unconstrained DelegationThe service can impersonate the user to any other service in the domain; the user's TGT is forwarded and cached in memory on the delegating serverVery High
Constrained DelegationThe service can only impersonate the user to a pre-defined list of target SPNs (msDS-AllowedToDelegateTo)Moderate
Resource-Based Constrained Delegation (RBCD)The target resource defines which accounts are allowed to delegate to it (msDS-AllowedToActOnBehalfOfOtherIdentity) — inverts the trust modelModerate
// Warning

Unconstrained delegation is one of the highest-risk misconfigurations in AD because a compromised server with this setting caches the TGTs of every user who authenticates to it — including Domain Admins.

3.8 Where Attack Techniques Fit In (Conceptual Only)

This section explains where these techniques intersect with the authentication flow described above — not how to execute them.

TechniqueWhere It Fits
Golden TicketForges a TGT from scratch using a stolen krbtgt hash, bypassing Step 1–2 entirely
Silver TicketForges a service ticket using a stolen service account hash, bypassing Steps 3–4
KerberoastingRequests a legitimate service ticket (Step 3–4) for offline analysis, targeting weak service account passwords
AS-REP RoastingTargets Step 1–2 against accounts with Kerberos pre-authentication disabled
Pass-the-TicketReuses a captured/exported ticket (TGT or service ticket) on a different host, skipping the normal request steps
Overpass-the-HashUses an NT Hash (or AES key) to request a legitimate TGT at Step 1, converting an NTLM-style credential into a Kerberos ticket
Skeleton KeyA malware technique that patches LSASS on a DC to accept a master password for any account, bypassing normal Step 1–2 validation
// Note

Every one of these techniques targets a specific message or key in the six-step flow above. That's the entire point of learning the protocol first — attack techniques stop looking like magic once you can point to the exact step they abuse.

Section 4 — LDAP Authentication

LDAP (Lightweight Directory Access Protocol) is how clients query and modify the Active Directory database itself. Authentication to LDAP is a separate concern from Kerberos/NTLM, though it's often layered on top of them.

4.1 Bind Types

Bind TypeDescriptionSecurity
Anonymous BindNo credentials supplied at allShould be disabled; only base-level info exposed by default
Simple BindPlaintext username + password sent to the DCInsecure unless combined with TLS (LDAPS)
SASL Bind (Kerberos/NTLM)Uses Kerberos or NTLM under the hood via SASL/GSSAPISecure — no plaintext credentials on the wire
// Warning

A Simple Bind over unencrypted LDAP (port 389) sends the password in cleartext. This is one of the most common findings in internal penetration tests — applications and scripts hardcoding LDAP simple binds without SSL.

4.2 LDAP Signing and LDAP over SSL

  • LDAP Signing cryptographically signs LDAP traffic to prevent tampering/relay, without necessarily encrypting the contents.
  • LDAPS (LDAP over SSL/TLS), port 636, encrypts the entire session, protecting simple binds from cleartext exposure.
graph TD A["Client"] -->|Port 389 - Simple Bind, no signing| B["DC - Cleartext credentials exposed"] A2["Client"] -->|Port 389 + LDAP Signing| C["DC - Signed, tamper-resistant"] A3["Client"] -->|Port 636 - LDAPS| D["DC - Fully encrypted"]
Fig. 9 — LDAP bind security comparison

4.3 How LDAP Is Used After Authentication

Once bound, LDAP is the query language for essentially everything in AD: user lookups, group enumeration, GPO reads, computer object attributes, and schema queries. Kerberos and NTLM tell the DC who you are; LDAP is how you then ask questions about the directory.

4.4 Demonstrating LDAP

bash — ldapsearch
ldapsearch -x -H ldap://dc01.contoso.local -D "jsmith@contoso.local" -w 'password' \
  -b "DC=contoso,DC=local" "(objectClass=user)"
powershell
Get-ADUser -Filter * -SearchBase "DC=contoso,DC=local"
wireshark filter
ldap
// Tip

If you see bindRequest frames in Wireshark carrying a visible password field, that's a simple bind over an unencrypted channel — flag it immediately in an assessment.

Section 5 — Certificate Authentication

5.1 Active Directory Certificate Services (AD CS)

AD CS is Microsoft's PKI implementation, allowing certificates to be issued for authentication (among other uses like code signing and TLS). Certificate-based authentication provides an alternative to password-based logon entirely.

5.2 PKINIT

PKINIT is the Kerberos pre-authentication extension that allows a client to authenticate to the AS (Step 1 of the Kerberos flow) using a certificate and private key instead of a password-derived key.

sequenceDiagram participant Client participant CA as Certificate Authority participant AS as Authentication Service (KDC) Client->>CA: Enroll for certificate (smart card / auto-enrollment) CA-->>Client: Issued certificate + private key Client->>AS: AS-REQ signed with certificate private key (PKINIT) AS->>AS: Validate certificate chain, map to AD account AS-->>Client: AS-REP (TGT) — same as password-based flow from here on
Fig. 10 — PKINIT certificate-based authentication

5.3 Smart Cards

Smart cards store the private key on a hardware token, requiring physical possession plus a PIN — turning authentication into a true multi-factor scheme (something you have + something you know).

5.4 Authentication Flow Summary

  1. Client presents a certificate to the KDC via PKINIT during AS-REQ
  2. The KDC validates the certificate against a trusted CA chain and maps it to an AD account (via UPN or explicit mapping)
  3. From AS-REP onward, the flow is identical to standard Kerberos — TGS-REQ, TGS-REP, AP-REQ, AP-REP all proceed unchanged

5.5 AD CS Misconfigurations (Brief Overview Only)

IDNameCategory
ESC1Misconfigured certificate template allows a requester to specify an arbitrary SANTemplate misconfiguration
ESC2Template permits "Any Purpose" or no defined EKU, allowing broad certificate misuseTemplate misconfiguration
ESC8AD CS web enrollment endpoint (HTTP) is vulnerable to NTLM relay for certificate requestsRelay-based
// Note

These are named here only for completeness and orientation — a full technical treatment of AD CS abuse belongs in a dedicated article on Kerberos/PKI attacks, not this foundational guide.

Section 6 — Integrated Windows Authentication

Integrated Windows Authentication (IWA) allows browsers and applications to authenticate transparently using the user's current domain session — no credential prompt required.

6.1 How Browsers Authenticate

When a browser encounters a WWW-Authenticate: Negotiate header from a web server, it attempts to use the currently logged-on user's Kerberos ticket (if the site is in the browser's trusted intranet zone) rather than prompting for credentials.

6.2 How IIS Authenticates

IIS supports multiple authentication providers, negotiated via the Negotiate mechanism:

graph TD A["Browser Request"] --> B{"WWW-Authenticate: Negotiate"} B --> C{"Kerberos ticket available and SPN valid?"} C -->|Yes| D["Kerberos authentication (AP-REQ/AP-REP)"] C -->|No| E["Fallback to NTLM challenge-response"]
Fig. 11 — IIS Negotiate authentication decision path
ProviderMechanismNotes
NegotiateChooses Kerberos first, NTLM as fallbackRecommended default
Kerberos (explicit)Kerberos only, no NTLM fallbackRequires correct SPN registration on the IIS app pool identity
NTLM (explicit)NTLM onlyUsed when Kerberos isn't viable

Demonstrating with IIS:

powershell
# Check configured authentication providers for a site
Get-WebConfiguration -Filter /system.webServer/security/authentication/windowsAuthentication -PSPath "IIS:\Sites\Default Web Site"

# Verify SPN registration for the app pool identity

If the SPN for a web application isn't registered correctly, IIS silently falls back to NTLM — reintroducing the weaker protocol even in an environment that "should" be using Kerberos.

Section 11 — Packet Capture Walkthrough

A typical domain logon touches all four core protocols in sequence. Here's what to expect when following the traffic in Wireshark, in the order it appears on the wire.

DNS

wireshark filter
dns

Expect an SRV query for _ldap._tcp.dc._msdcs.<domain>, followed by an A record lookup for the returned hostname.

Kerberos

wireshark filter
kerberos

Expect AS-REQ → AS-REP for the initial TGT, followed by one or more TGS-REQ/TGS-REP pairs as the client requests service tickets for each resource it touches.

LDAP

wireshark filter
ldap

Expect bindRequest (usually SASL/GSS-SPNEGO wrapped, not simple bind, on a properly configured domain), followed by searchRequest/searchResEntry pairs as Group Policy and directory lookups occur.

SMB

wireshark filter
smb2

Expect Session Setup Request/Response frames carrying the Kerberos AP-REQ/AP-REP (or NTLM messages, if Kerberos wasn't used), followed by Tree Connect to the specific share.

// Tip

Correlate frames by timestamp proximity and source/destination IP — a real logon produces a tight, predictable cluster: DNS → Kerberos AS exchange → Kerberos TGS exchange → LDAP → SMB, typically all within a couple of seconds.

Section 13 — Key Takeaways

  • Windows never sends or stores plaintext passwords — everything downstream is built on the NT Hash, derived once and reused for all subsequent cryptographic operations.
  • DC Locator (DNS SRV records + Netlogon) has to succeed before any authentication protocol can even begin.
  • NTLM is a challenge-response protocol: three messages (NEGOTIATE → CHALLENGE → AUTHENTICATE), no ticket, no mutual authentication, and a persistent fallback risk.
  • Kerberos is a six-message ticket-based protocol (AS-REQ → AS-REP → TGS-REQ → TGS-REP → AP-REQ → AP-REP) offering mutual authentication and reduced DC load.
  • The krbtgt account and individual service account keys are the highest-value credentials in the domain because they encrypt TGTs and service tickets respectively.
  • LDAP authentication (bind) is a separate concern from Kerberos/NTLM, but is frequently layered on top of it via SASL/GSSAPI.
  • Certificate-based authentication (PKINIT) replaces only the first Kerberos step — everything from AS-REP onward is unchanged.
  • Integrated Windows Authentication is just Kerberos/NTLM wrapped in the Negotiate HTTP mechanism — the same rules and failure modes apply.
  • Every major AD attack technique maps directly onto a specific message or key in the flows described in this article. Once you can point to exactly which step an attack targets, the attack itself becomes far easier to understand — and to defend against.
